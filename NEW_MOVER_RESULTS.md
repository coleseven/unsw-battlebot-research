### M1 code (1 Oct)

- C++ (`cppbot/v6_brain.hpp`, `cppbot/mover.hpp` generated by
  `bcsim.gen_cpp` from `framework/mover_r5.json`, zero weights when absent):
  `MoverTrace` filled by `score_moves` (24 v3 inputs, complete score S0 and
  its v3 part, 28 candidate features) and `decide` (12 decision features);
  `mover_choice` applies q = q0 + lambda 2 tanh f (q0 = (S0 - mean) / scale)
  and overrides the incumbent only if q gains more than tau; non-finite output
  returns the incumbent. Eligible: no attack candidate, >= 2 ordinary moves.
  Switches CPP_MOVER, CPP_MOVER_LAMBDA, CPP_MOVER_TAU, CPP_MOVER_LOG (log every
  N-th eligible decision by (31 id + round) mod N; LOG lines only).
- Training reads the C++-logged features directly, so there is no second
  (Python) feature implementation to drift; inference parity (Python forward
  vs C++ `mover_forward`) is an M5 check.
- **Parity gate PASSED** (`results/mover-m1-parity.json`): 16 games (Portals,
  Trophy, PD, Maze x v92 and v7-base x both sides): the new build with the mover
  off, with zero-weight mover on, and with logging every 8th decision all play
  identically to versions/v10h; every logged decision has 64 features.
- Feature sanity (7,235 candidate rows, Portals/Default/Australia vs v92): no
  NaN, ranges as designed. Always 0 here: blocks-recipient-front (56) and
  recipient-visible (57) - a dragon beside a visible king feeds instead of
  moving, so these states rarely reach a move decision; kept, documented.
  Candidate-feature names in `bcsim/mover_teacher.py` (FEATURES).
- Context: the Sprint (1 Oct, unseen maps) showed v10h wins only 58/168 on
